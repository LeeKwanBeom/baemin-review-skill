# baemin-review 정기 점검표 (정본)

이 파일이 점검 절차의 정본이다. 사용자는 짧은 지시만 붙여넣고,
실제 절차는 이 파일을 읽어서 수행한다.

**이 파일은 매 회차 갱신된다.** 점검이 끝나면 "점검표 개정안"에서 사용자가
채택한 것만 반영한다. **커밋은 두 번이다** — `audit/last-audit.md` 를 먼저(1차),
사용자가 개정안을 채택한 뒤 이 파일을 나중에(2차) 올린다. 두 파일을 한 커밋에
같이 넣으려 하지 마라. "채택 여부를 묻기 전에 이 파일을 고치지 마라"와 동시에
성립하지 않는다(1회차에서 확인). 자세한 순서는 아래 [마무리 — 기준선 갱신] 절을
그대로 따른다 — 이 머리말과 그 절은 항상 같은 말을 해야 한다.

버전: v6 (2026-09-23 수정 회차 2 — 검증 회차(2026-09-21) 결과 처리: "되돌리면 안 되는 것" 표의 throttled 행에 라운드 시작 hidden 게이트·바닥 판정 가드·`lastGainY` 되감기 반영, [실행 준비 조건]의 숨김 계측에 되감기·2회 연속 조건 추가. v5: 2026-09-20 2회차 수정 회차 — 개정안 1~13 채택: 속도 기준선 표·벽시계 분해 상시화(실험 절은 속도 목표 회차만), localStorage 집합 보관, audit-only 계측 허용, 사본 dry-run, 바이트 수 금지·행 번호 기준 명시, 문구 교체는 파일 전체 검색, C 항목 BLOCKED/TRUNCATED, hidden 재발 경고, F 실험 절차, 배너 격하, 파트너전용 라벨 대조, 의도된 동작에 칩 기록 추가, "되돌리면 안 되는 것" 표 갱신. v4: 2026-09-09 교차 정정 회차 — 쿠팡 스킬 점검 개정안 이관: [시작 전 확인 ③]의 백업 위치를 `$HOME/skillwork` → `$HOME/mnt/claude/backup/` 로 바꾸고 사유 명시. 326행 skillwork 는 임시 작업 공간이라 유지. v3: 2026-09-09 정정 회차 — 머리말의 "같은 커밋으로" 를 [마무리] 절의 2회 커밋 규칙과 일치시킴, [판정 기준]에 "행 번호 대신 절 이름·함수명" 항목 추가. v2: 1회차 점검의 개정안 10건 + "PC에서 push" 절차 반영. v1: 같은 날 saero·hometax 점검표를 이 스킬 구조에 맞춰 옮김)

아직 고치지 말고 진단만. 뭘 고칠지는 사용자가 고른다.

[시작 전 확인 ① — 토큰부터 확보한다]

**진단을 시작하기 전에 push 토큰을 먼저 요청해라.** 마무리에 저장소로 두 파일을
올려야 하는데, 진단이 다 끝난 뒤에 요청하면 그 사이 세션이 끊길 때 결과가
통째로 유실된다. 다른 스킬 점검에서 실제로 그렇게 한 세션이 날아갔다.

요청 문구에 토큰이 안 보이면 **첫 응답에서** 이렇게 물어라:

> 점검을 시작하겠습니다. 마무리에 기준선과 점검표를 올려야 해서
> `baemin-review-skill` push 토큰(Contents: Read and write)이 필요합니다.
> 지금 주시면 진단 후 바로 올리고, 없으면 파일로만 드리겠습니다.

토큰 없이 진행하기로 했으면 진단 도중에도 중간 산출물을 파일로 먼저 내려주고
마지막에 다시 알려라. 토큰은 대화에 남으니 작업이 끝나면 폐기하라고 안내할 것.

[시작 전 확인 ② — 정본이 두 곳에 있다. 어느 쪽이 최신인지부터 확인해라]

saero·hometax 와 구조가 다르다. **부트스트랩 방식이 아니다.**
저장소는 기록 보관소이지 실행 경로가 아니다.

| 무엇 | 어디 | 역할 |
|---|---|---|
| 실행 본문 | 설치본 — 경로는 스킬 호출 헤더의 `Base directory for this skill:` 줄이 알려준다 (2026-09-09 실측: `/root/.claude/skills/synced/<uuid>_<uuid>/baemin-review/SKILL.md`. 예전 점검표의 `/mnt/skills/plugins/...`는 이 환경에 없다) | 스킬이 실제로 읽고 도는 것 |
| 사본·정본 | 저장소 `SKILL.md` | 수정은 여기서 하고 `.skill` 로 패키징 |
| 점검표·기준선 | 저장소 `audit/` | 이 파일과 회차 기록 |

- **설치 경로는 세션마다 패키지에서 다시 풀린다.** 거기에 쓴 것은 보존되지 않는다.
  고친 내용을 남기려면 저장소에 push 하고, `.skill` 로 다시 패키징해
  **사용자가 Claude 설정에서 재업로드**해야 실행에 반영된다.
- **저장소와 설치본이 다를 수 있다.** 저장소만 고치고 재업로드를 안 했으면
  설치본이 옛것이고, 설치본만 고쳤으면 그 수정은 세션이 끝나며 사라졌다.

**시작하면서 둘을 대조해라.**

```bash
git clone https://github.com/LeeKwanBeom/baemin-review-skill
md5sum baemin-review-skill/SKILL.md "<스킬 호출 헤더의 Base directory>/SKILL.md"
```

- **md5 동일** → 정상. 그대로 진행한다.
- 사용자 폴더(`$HOME/mnt/claude`)의 `baemin-review.skill` 패키지 파일도 최신인지 본다 — 2026-09-09에는 7/26자 패키지가 남아 있어 9/6 개정 이전 것으로 보였다. 오래됐으면 "재패키징 시 이 파일을 갱신할 것"으로 보고에 적는다(실행에는 영향 없음).
- **다름** → 어느 쪽이 최신인지 판정하고 **그 사실부터 보고해라.**
  저장소가 최신이면 "재업로드가 안 된 것"이고, 설치본이 최신이면
  "저장소에 push 가 안 된 것"이다. 둘은 대응이 다르다.
  진단은 **저장소 사본을 기준으로** 하되, 설치본과 다른 부분은 따로 적어라.
- `NO_BASELINE` → "기준선 파일 없음"이라고 명시하고 신규 진단으로 진행한다.

[시작 전 확인 ③ — 실제 실행 없이는 진단이 절반이다]

이 스킬은 브라우저 자동화다. 문서를 읽는 것만으로는 셀렉터가 아직 맞는지,
스크롤이 정체되는지, 파싱이 되는지 판정할 수 없다.
**사용자가 정한 방침이기도 하다: "개선 후 실제 사이트에서 실행 테스트".**

그러므로 이 점검은 **실제 1회 실행을 포함한다.** 다만 조건이 있다.

- **엑셀을 먼저 백업해라.** 이 스킬은 스냅샷 동기화라 실행이 기존 행을 지운다.
  백업은 사용자 폴더 아래 `$HOME/mnt/claude/backup/` 에 둔다. 없을 수 있으니 먼저 만든다.
  **`$HOME/skillwork` 에 두지 마라 — 세션별 홈이라 세션 종료 시 접근 불가(2026-09-09 쿠팡 점검 실측).
  세션이 끝나면 못 꺼내므로 백업 구실을 못 한다.**
  ```bash
  mkdir -p "$HOME/mnt/claude/backup" && cp "$HOME/mnt/claude/배민_저점수리뷰.xlsx" "$HOME/mnt/claude/backup/배민_백업_$(date +%Y%m%d_%H%M).xlsx"
  ```
- **Step 5(엑셀 저장)는 실제 파일 대상으로는 실행하지 마라. 엑셀 사본 dry-run 은 한다.**
  Step 0~4 를 돌린 뒤 5-1 JSON 을 기록하고 5-2 저장 스크립트의 두 번째 인자를 **사본 경로**
  (`cp` 해 둔 파일)로 바꿔 돌려 `new/deleted/rows/verified` 를 본다. 실제 파일의 mtime·md5 가
  그대로인지 끝에 확인해라. 2026-09-20 수정 회차에서 이 방식으로 저점수 1건 추가·멱등·ok:false
  보존·삭제 동작(T1~T4)을 검증했다. 점검은 진단이지 갱신이 아니다.
- 브라우저·로그인이 준비돼 있지 않으면 사용자에게 요청하고 기다려라.
  계정A(김치찜·곱도리) / 계정B(참 제육) 두 번의 로그인이 필요하다.
- **크롬 창이 다른 창에 가려지지 않게 화면 앞에 두어야 한다.** 새 탭은
  `document.hidden === true`로 시작하는 것이 기본값에 가깝고(2026-09-09 실측 2/2),
  그 상태에서는 타이머가 1초로 늘고 리스트가 로드되지 않는다. SKILL.md Step 2가
  이를 게이트로 잡지만, 점검에서는 **가려진 상태와 꺼낸 상태 둘 다 한 번씩 계측**해
  `throttled` 신호가 `reason:'hidden'` 으로 뜨고(가짜 `bottom:true` 0회), `lastGainY` 로 되감은 뒤 재개해
  `collected + blocked === expectedTotal` 로 복구되는지 확인한다(사용자에게 가려달라/꺼내달라 요청).
  숨김 호출 2회 연속 조건도 1회 포함한다(2026-09-21 검증 회차에서 되감기 없이는 87/89).
- **사용자가 Claude 앱에서 답장을 쓰는 동안에도 크롬이 가려져 `hidden` 이 다시 `true` 가 된다**
  (2026-09-20 곱도리 실측). 점검 중 사용자에게 메시지를 보낼 때마다 이 일이 생길 수 있으니
  매장마다 스크롤 직전(SKILL.md Step 3-1)에 `hidden` 을 다시 본다.
- **표준 계측(매 회차 고정):** 탭 생성 직후 `document.hidden`, `setTimeout(250)` 실측
  5회, 매장별 `expectedTotal`·`collected`·`blocked`·`countMatch`·`parseFail`·`_scroll` 호출 수·
  라운드 합·`avgRoundMs`·`elapsedMs` 합·벽시계(navigate→Step 4 결과, 사용자 대기 제외/포함)·
  도구 호출 수·hidden 시작값 — 기준선의 **"속도 기준선" 표**와 **"벽시계 분해" 표**(페이지 로드 /
  사이트 렌더링 / 도구 왕복·코드 생성 / 사용자 대기)를 매 회차 채운다. 이 두 표는 상시다.
  **속도 후보의 A/B 실험 절은 사용자가 속도를 목표로 지시한 회차에만 한다**(회차당 10~20분과
  계정 재로그인 1회가 든다). 이 숫자들이 기준선의 "실행 실측 기록"과 대조된다.
- **리뷰번호 집합은 같은 오리진 `localStorage` 에 보관해라**(예: Step 4 직후
  `localStorage.setItem('_audit_A_<매장>', JSON.stringify({ all: window._all, blocked: window._blocked, warn: window._warn }))`).
  navigate·재로그인 뒤에도 남아 A/B 대조를 페이지 안에서 끝낼 수 있고, 도구 반환 1,000자
  한계를 우회하는 유일한 저비용 방법이다(2026-09-20 실측). 점검이 끝나면 지우되, 검증 회차가
  대조할 필요가 있으면 남겨 두고 기준선에 적는다.
- **audit-only 계측은 허용한다.** 반환 JSON 에 타이밍 필드(`t`, `sinceNav`)를 얹거나 위와 같은
  `localStorage` 대입 한두 줄을 넣는 것은 된다. 단 **판정 로직(`ok`·`reason`·종료 조건·`_parse`)은
  건드리지 않는다.** 넣은 줄은 기준선 "실행 실측 기록"에 그대로 적어라.
- 매장 정보 표(shopId 3개·계정 A/B)는 실행이 통과하면 자동으로 확인된 것이다.
  따로 항목으로 판정하지 않는다(1~3회차 연속 통과).

실행이 불가능하면(브라우저 미연결, 로그인 불가) 그 사실을 명시하고
**실행으로만 확인되는 항목을 전부 [추론]으로 표시해라.** 문서만 읽고
"셀렉터가 맞다 / 스크롤이 정상이다" 라고 쓰지 마라.

[0단계 — 기준선 대조. 신규 진단보다 이걸 먼저]

저장소의 `audit/last-audit.md` 를 먼저 읽어라. 이게 정본이다.
없으면 "기준선 파일 없음"이라고 명시하고 (2)로 넘어가라.

(1) 거기 적힌 항목을 지금 실물에서 하나씩 다시 확인해라.
    해결됨 — 수정 내용이 실물에 있다 (수정된 원문 인용)
    미해결 — 예전 상태 그대로다 (지금 원문 인용)
    근거없음 — 그때 지적 자체가 실물 근거가 없었다 (한 줄 사유)
    요약하지 말고 원문을 붙일 것.

(2) **설치본과 사용자 사본이 어긋났는지 양방향으로 확인해라.**
    - 사용자가 재업로드를 안 했으면 → 지난 회차 수정이 설치본에 없다
    - 설치본에는 있는데 기준선에 기록이 없으면 → 누군가 기록 없이 고친 것
    지난 회차 기준선에 "수정함"으로 적힌 항목이 설치본에 없으면,
    **재업로드가 안 된 것이지 수정이 실패한 게 아니다.** 그 구분을 명확히 적어라.

(3) 그다음에 기준선에 없던 신규 항목만 찾아라.

[직전 회차가 남긴 것 — 기준선의 "다음 점검에서 대조할 것"을 읽어라]

회차마다 이 절에 새 항목을 쓰지 않는다. 직전 회차가 남긴 미확정·미실측 항목은
`audit/last-audit.md`의 "미확정으로 남긴 것"과 "다음 점검에서 대조할 것"에 있다.
그 항목을 0단계 (1)과 같은 방식으로 해결됨/미해결/근거없음 또는 판정완료/미확정으로
다시 판정한다. 저장소 밖 인계 문서(사용자 폴더의 md 등)는 입력물로 쓰되,
다음 회차를 위해 그 내용을 기준선에 흡수하고 나서 끝내라.

(1회차의 인계 A~D·미확정 1~2는 2026-09-09 기준선에 판정·흡수했다. 여기서 다시 다루지 않는다.)

[의도된 동작 — 결함으로 올리지 마라]

아래는 사용자가 알고 선택한 것이거나 SKILL.md "설계 근거"에 이유가 적힌 것이다.
"고치면 좋겠다"는 생각이 들어도 결함이 아니다. 바꾸려면 사용자 승인이 필요하다.

- **엑셀이 스냅샷 방식이라 조회 기간 밖 과거 리뷰가 지워진다.**
  사용자가 알고 선택했다. 이 엑셀은 누적 아카이브가 아니라 최근 현황판이다.
- **API를 쓰지 않고 DOM 을 긁는다.** `self-api.baemin.com` 은 크로스 오리진
  차단이라 헤더를 맞춰도 안 된다(2026-09-05 실측). 쿠팡 방식을 이식하려 하지 마라.

■ A. 문서와 코드가 어긋나는 곳
   - 매장 정보 표(shopId 3개·계정 A/B)가 실제 URL·로그인과 맞는지
   - 트러블슈팅 표의 증상·원인·대응이 실제 코드 동작과 맞는지
     (1회차의 "hidden 전제" 오류가 이 유형이었다 — 기준선 결함 1)
   - 실측 수치(2026-09-20 기준: 김치찜 175건 83라운드·6.9초·곱도리 87건 3.9초·참 제육
     91건 4.2초, 라운드당 83~98ms, 349/349 색상 경로, DOM 카드 8~13개, 카드 높이 중앙값

   - Step 간 값 인계(`expectedTotal`·`filterOk`·`authExpired`·`SID`)가 끊기는 지점

■ B. 셀렉터·정규식이 현재 사이트와 맞는지  ※ 실행으로만 판정 가능
   - `ReviewContent-module` 클래스가 아직 존재하는지
   - 별점: 카드에 `aria-label` 이 생겼는지(2026-09-09 에는 0개), SVG 색상 경로가
     여전히 381/381 처럼 전건 읽는지, 카드 안에 새 노란 아이콘이 생겼는지
   - `전체(N)` 표기가 그대로인지
   - 기간 다이얼로그의 `input[type="radio"]` + `label[for]` 구조가 유지되는지
   - 배달유형 목록(`DT`, 2026-09-20 부터 `픽업` 포함)·비공개 키워드(`PK`)·파트너전용 라벨
     정규식(`PK_LABEL`)에 새로 생긴 값·형식이 있는지. 매장 첫 줄 분포를 한 번 집계한다
   - **파트너전용 라벨 카드 1건을 화면과 대조한다**(`파트너님에게만 보이는 리뷰입니다.`):
     `reviewText` 가 `[파트너전용] 본문` 한 번만 담는지. 저점수가 희소해 저장 결과로는
     드러나지 않는 유형이다(2026-09-20 결함 3). 표본은 직전 기준선의 리뷰번호 목록
   - 하단 프로모션 배너(`[class*="FloatingBanner-module"]`, fixed z-index 101, role 없음):
     2회 연속(2026-09-09·09-20) 기간 버튼·적용 버튼과 겹치지 않았고 JS `.click()` 경로는
     영향 없음. **레이아웃 변경이 의심될 때만** 다이얼로그 개폐 상태별 `elementFromPoint` 로 확인

■ C. 조용한 실패가 가능한 경로
   이 스킬의 최대 위험은 "조용히 0건"이다. 아래를 코드에서 짚어라.
   - `gained === 0` 이 세션 끊김 때문인지 진짜 끝인지 구분하는 장치가 살아있는지
   - `ok: false` 인데도 저장 단계로 넘어가는 경로가 있는지
   - `parseFail` 10% 초과·`수집 + 게시중단 < 전체(N)` 판정이 살아 있는지(2026-09-20 채택)
   - **도구가 결과를 차단·절단하는 경로**: 반환 JSON 에 쿼리스트링이 든 URL 이 들어가면
     `[BLOCKED: Cookie/query string data]`, 약 1,000자를 넘으면 끝에 `[TRUNCATED]`. 판정값이
     이 경로에 걸려 안 보이는 곳이 있는지(2026-09-20 결함 2 가 이 유형)
     ※ 판단이 갈리면 결함이 아니라 개선안으로

■ D. 검증이 비어 있는 구간  ※ 결과는 전부 개선안으로 분류
   - 저장 후 엑셀을 다시 열어 행수·형식을 확인하는 단계가 없다
   - 3개 매장 결과를 합칠 때 `storeName` 오타를 잡는 장치가 없다
   - `reviews` 배열이 비었는데 `ok: true` 인 경우를 구분하는 장치
   - 백업 자동화(스냅샷 방식이라 실행 전 백업이 사실상 필수인데 절차에 없다)

■ E. 자동화·구조 개선 후보  ※ 결과는 전부 개선안으로 분류
   - 600행대 단일 문서를 절차/코드/판정으로 나눌지
   - 쿠팡 스킬과 공유 가능한 부분(엑셀 저장 로직·날짜 정규화)이 있는지
   - 매장 정보를 문서 본문이 아니라 별도 설정으로 뺄지

■ F. 별도 실험(선택 — 정상 실행 계측과 양립하지 않으므로 필요할 때만)
   - Chrome intensive throttling. **절차:** 정상 계측이 끝난 뒤 페이지에 연쇄
     `setTimeout(250)` 로거(콜백 안에서 재예약, `[경과ms, 간격ms, hidden]` 기록 + `visibilitychange`
     기록)를 심고 사용자에게 창을 5분 이상 가려 달라고 요청, 30초 버킷으로 평균·최대 간격을 읽는다.
     사용자가 Claude 앱을 안 보는 환경(두 모니터 등)에서는 자연 발생하지 않으므로 반드시 요청한다.
     **2026-09-20 실측:** 숨김 0~60초 1초 클램프 → 약 70초부터 60,000ms 정렬(7회 연속). 반면 새
     호출로 시작한 `await setTimeout(250)` 6회 연쇄는 같은 상태에서 1초 클램프만(60초 정렬 없음).
     45초 CDP 타임아웃 기전으로는 약해졌고 남은 후보는 렌더러 동결 — 재현되면 그때 잰다

  개행이 없어 `wc -l` 과 실제 줄 수가 1 다르므로, **행 번호를 인용할 때 어느 기준인지 적는다**
  (2회차 기준선은 실제 줄 번호 = Read 도구 번호). 쿠팡 스킬 정정 1 이관.
- **개수를 적을 때는 세어서 적어라.** "지적 4건" 처럼 숫자를 쓸 거면 실제로 세라.
  기록의 숫자가 틀리면 다음 회차가 그걸 기준으로 판정한다.
- **기록 문구는 방향·범위·개수를 원문에서 확인하고 적어라.** 코드는 맞는데
  문구만 틀린 오류가 다른 스킬 점검에서 반복해서 나왔다.
- **수정 회차의 기록은 행 번호 대신 절 이름·함수명으로 가리켜라.** 진단은 수정 전
  파일을 보고 쓰는데 기록은 수정 후 파일과 함께 남는다 — 행이 밀려 어긋난다.
  2026-09-09 수정 회차가 실제로 그랬다: 599행 기준으로 적은 "221행"이 636행 파일에도
  **실재하는 다른 주석**(카드 경계 = 결함 4)을 가리켜, 다음 회차가 결함 2를 그 줄로
  판정할 뻔했다. 없는 행을 가리키면 금방 들키지만 있는 행을 가리키면 조용히 틀린다.
  결함을 **지적**할 때는 지금 보고 있는 파일의 행 번호 + 원문을 그대로 인용하되(이건
  그대로 유지), **수정 기록**에는 `Step 2 `_parse` 별점 주석`처럼 절·함수로 적고
  행 번호를 함께 쓸 거면 **몇 행짜리 파일 기준인지 반드시 붙여라**(`636행 기준 231~235`).
- **직전 세션의 판단을 결론으로 받지 마라.** 인계 문서가 있으면 그것은 입력물이지
  확정이 아니다. 각 항목을 실물에서 다시 판정해라.

- 점검표가 잘못 전제하고 있는 것 (파일 경로, 실측 수치, 의도된 동작 목록 등)

- 저장소가 없는 구조 때문에 안 맞는 절차

이건 결함·개선안 어디에도 넣지 말고 "점검표 개정안"으로 따로 내라. 개수 제한 없다.

[지적 채택 규칙 — 개수보다 이게 중요하다]

- 지적하려면 **줄 번호 + 문제되는 원문**을 인용해야 한다. 인용할 수 없으면
  지적하지 말고 통과 처리해라. 인용을 못 해서 제외한 항목이 몇 개인지
  마지막에 숫자로 알려줘.
- 아래 둘을 한 목록에 섞지 마라. 분리해서 따로 내라.
  결함 : 지금 이미 틀렸거나, 특정 조건에서 반드시 틀려지는 것
  개선안 : 있으면 좋은 것 / 자동화 후보 / 검증이 비어 있는 구간
  D·E 는 성격상 전부 개선안이다.
- 개선안은 최대 5개. 매번 새로 만들어내지 말고, 기준선에 이미 적힌 개선안이
  있으면 그걸 다시 쓰고 순위만 갱신해라.

[결과 정리 방식]

결함을 심각도 순으로, 항목마다:
- 지금 이미 틀렸는지 / 앞으로 틀려질 건지 (틀려진다면 언제)
- 실측으로 확인한 건지 추론인지
- 고치면 실제로 뭐가 달라지는지
- **작업 경로. 세 단계이고 하나라도 빠지면 미완이다:**
  · 저장소 `SKILL.md` 수정 → push
  · 그걸로 `.skill` 재패키징
  · **사용자가 Claude 설정에서 재업로드**
  재업로드 전에는 실행에 반영되지 않는다. 결과에 그 사실을 반드시 명시해라.
  저장소만 고치고 "완료"라고 하지 마라.

[수정 회차에 적용할 것 — 이 절은 진단이 아니라 다음 단계용이다]

이번 회차는 진단만 한다. 다만 여기서 나온 결함을 **고칠 때** 아래를 지켜야
같은 회차 안에서 새 결함이 생기지 않는다. 진단 보고서 끝에 이 절을 그대로
옮겨 적어 다음 단계가 읽게 해라.

- **수정은 저장소 `SKILL.md` 에서 한다.** 설치본을 직접 고치면 세션이 끝나며
  사라진다. 저장소에 push 한 뒤 그것으로 패키징해라.
- **한 번의 수정 → 한 번의 패키징 → 한 번의 재설치.**
  중간에 다른 세션을 열면 그 세션은 옛 캐시를 읽고 그 위에 수정한다.
  먼저 한 수정이 조용히 사라진다. 실제로 겪은 사고다.
- **수정 후 반드시 파일을 다시 열어 눈으로 확인하고 나서 "완료"라고 말해라.**
  사용자가 정한 상시 방침이다. 확인 없이 완료를 선언하지 마라.
- **고친 뒤 실제 사이트에서 1회 실행해라.** 사용자가 정한 방침이다.
  문서만 고치고 끝내지 마라.
- **같은 개념을 두 곳에서 고칠 때는 기준을 대조해라.** 이 문서는 절차·코드·
  트러블슈팅 표에 같은 규칙이 세 번 나오는 곳이 있다. 한 곳만 고치면 어긋난다.
- **문구 교체는 지목된 곳이 아니라 파일 전체 검색으로 처리해라.** 개정안·결함이
  "A 절의 이 문장을 고쳐라" 라고 짚어도, 그건 **발견된 곳**이지 **전부**가 아니다.
  고치기 전에 옛 문구의 핵심 어절로 `grep` 해 같은 파일·자매 파일(SKILL.md ·
  checklist.md · README.md)에서 동일 취지의 문장을 **전부** 찾아 함께 고치고,
  고친 뒤 같은 검색을 다시 돌려 남은 것이 무관한 문장인지 확인해라. 남아 있으면
  한 파일이 두 말을 하게 된다(쿠팡 스킬 v2.1 규칙 이관. 2026-09-20 수정 회차는 종료 조건·hidden·
  잘림 표기를 이 방식으로 처리했다).
- **판정 조건을 완화하는 수정을 했으면 원래 잡히던 실패가 여전히 잡히는지
  다시 확인해라.** `ok` 판정과 `expectedTotal` 관련이 특히 그렇다.
- **"되돌리면 안 되는 것" 표에 있는 것을 건드렸으면 그 표도 같이 갱신해라.**
- **수정과 검증은 다른 세션에서 한다.** 진단한 쪽이 수정하지 않고, 수정한 쪽이
  검증하지 않는다. 다른 스킬 점검에서 검증이 잡아낸 것의 다수가 수정 과정에서
  새로 생긴 것이었다.

[마무리 — 기준선 갱신]

진단이 끝나면 저장소의 아래 두 파일을 갱신하고 push 한다. **커밋은 두 번이다** —
예전 문구("같은 커밋으로")는 "채택 여부를 묻기 전에 checklist.md 를 고치지 마라"와
동시에 성립할 수 없었다(1회차에서 확인). 순서:

1. **1차 커밋(진단 직후, 보고 전):** `audit/last-audit.md` 만. 아래 형식. 직전 회차
   기록은 파일 아래쪽에 "이전 기록" 으로 원문 보존해라. "점검표 개정안"은 이 파일
   안에 제안으로만 적는다. checklist.md 는 이 커밋에서 손대지 않는다.
2. **2차 커밋(사용자가 개정안을 채택한 뒤):** `audit/checklist.md` — 채택된 것만
   반영하고 머리말의 버전 줄을 갱신한다. 수정 회차라면 `SKILL.md` 와
   `last-audit.md` 의 "수정 기록" 절도 이 커밋에 함께 넣는다.

1차만 하고 세션이 끝나면 기준선은 남되 점검표는 옛것이다 — 다음 회차가 last-audit.md
의 개정안 절을 읽으면 복구된다. 2차 없이 끝냈으면 그 사실을 보고에 적어라.

**저장소의 `SKILL.md` 는 진단 회차에 고치지 마라.** 설치본과 md5 가 달랐다면
그 사실만 기준선에 적고, 어느 쪽으로 맞출지는 사용자가 정한다.

**순서를 지켜라: ① push → ② 재clone 확인(md5 대조) → ③ 그다음에 채팅 보고.**
채팅 보고를 먼저 길게 쓰면 세션이 끊길 때 저장소에 아무것도 남지 않는다.

**클라우드에서 push 가 막히면 PC 에서 push 해라.** 2026-09-09 실측: 클라우드
컨테이너의 git 프록시가 이 저장소를 "세션의 인가 저장소 목록에 없음"으로 403 을
냈다(`access denied by the git proxy`). 조직 정책 거부라 재시도해도 안 된다. 절차:
  1. 갱신할 파일을 `SendUserFile` → `device_commit_files` 로 사용자 폴더
     (`$HOME/mnt/claude/`)에 내려놓는다(어차피 "파일로도 내려줘" 요건이다).
  2. `device_bash` 로 PC 에서 clone → 파일 복사 → commit → push:
     ```bash
     mkdir -p $HOME/skillwork && cd $HOME/skillwork && rm -rf repo && git clone -q https://github.com/LeeKwanBeom/baemin-review-skill repo && cd repo
     cp "$HOME/mnt/claude/<내려놓은 파일>" audit/last-audit.md   # 필요한 파일마다
     git config user.email "<이메일>" && git config user.name "LeeKwanBeom"
     git add -A && git commit -q -m "<메시지>" && git push -q https://x-access-token:<토큰>@github.com/LeeKwanBeom/baemin-review-skill.git HEAD:main
     ```
     PC 의 git 은 네트워크가 열려 있었다(git 2.34.1, `git ls-remote` 성공).
  3. 재clone 으로 md5 를 대조하고, "PC 에서 push 했다"는 사실을 보고에 적는다.
  토큰은 명령줄에만 쓰고 remote 설정이나 파일에 남기지 않는다.

**진단 전문을 파일로도 내려줘. 채팅 요약본 말고 파일 자체가 필요하다.**
요약만 받으면 다음 세션으로 옮길 때 절반이 유실된다.

토큰을 못 받았으면 push를 건너뛰되 **두 파일을 반드시 파일로 내려주고**
"저장소에 반영되지 않았다"고 명시해라. 완료라고 말하지 마라.
