# baemin-review 정기 점검표 (정본)

이 파일이 점검 절차의 정본이다. 사용자는 짧은 지시만 붙여넣고,
실제 절차는 이 파일을 읽어서 수행한다.

**이 파일은 매 회차 갱신된다.** 점검이 끝나면 "점검표 개정안"에서 사용자가
채택한 것만 반영한다. **커밋은 두 번이다** — `audit/last-audit.md` 를 먼저(1차),
사용자가 개정안을 채택한 뒤 이 파일을 나중에(2차) 올린다. 두 파일을 한 커밋에
같이 넣으려 하지 마라. "채택 여부를 묻기 전에 이 파일을 고치지 마라"와 동시에
성립하지 않는다(1회차에서 확인). 자세한 순서는 아래 [마무리 — 기준선 갱신] 절을
그대로 따른다 — 이 머리말과 그 절은 항상 같은 말을 해야 한다.

버전: v3 (2026-09-09 정정 회차 — 머리말의 "같은 커밋으로" 를 [마무리] 절의 2회 커밋 규칙과 일치시킴, [판정 기준]에 "행 번호 대신 절 이름·함수명" 항목 추가. v2: 1회차 점검의 개정안 10건 + "PC에서 push" 절차 반영. v1: 같은 날 saero·hometax 점검표를 이 스킬 구조에 맞춰 옮김)

---

아직 고치지 말고 진단만. 뭘 고칠지는 사용자가 고른다.

[시작 전 확인 ① — 토큰부터 확보한다]

**진단을 시작하기 전에 push 토큰을 먼저 요청해라.** 마무리에 저장소로 두 파일을
올려야 하는데, 진단이 다 끝난 뒤에 요청하면 그 사이 세션이 끊길 때 결과가
통째로 유실된다. 다른 스킬 점검에서 실제로 그렇게 한 세션이 날아갔다.

요청 문구에 토큰이 안 보이면 **첫 응답에서** 이렇게 물어라:

> 점검을 시작하겠습니다. 마무리에 기준선과 점검표를 올려야 해서
> `baemin-review-skill` push 토큰(Contents: Read and write)이 필요합니다.
> 지금 주시면 진단 후 바로 올리고, 없으면 파일로만 드리겠습니다.

토큰 없이 진행하기로 했으면 진단 도중에도 중간 산출물을 파일로 먼저 내려주고
마지막에 다시 알려라. 토큰은 대화에 남으니 작업이 끝나면 폐기하라고 안내할 것.

[시작 전 확인 ② — 정본이 두 곳에 있다. 어느 쪽이 최신인지부터 확인해라]

saero·hometax 와 구조가 다르다. **부트스트랩 방식이 아니다.**
저장소는 기록 보관소이지 실행 경로가 아니다.

| 무엇 | 어디 | 역할 |
|---|---|---|
| 실행 본문 | 설치본 — 경로는 스킬 호출 헤더의 `Base directory for this skill:` 줄이 알려준다 (2026-09-09 실측: `/root/.claude/skills/synced/<uuid>_<uuid>/baemin-review/SKILL.md`. 예전 점검표의 `/mnt/skills/plugins/...`는 이 환경에 없다) | 스킬이 실제로 읽고 도는 것 |
| 사본·정본 | 저장소 `SKILL.md` | 수정은 여기서 하고 `.skill` 로 패키징 |
| 점검표·기준선 | 저장소 `audit/` | 이 파일과 회차 기록 |

- **설치 경로는 세션마다 패키지에서 다시 풀린다.** 거기에 쓴 것은 보존되지 않는다.
  고친 내용을 남기려면 저장소에 push 하고, `.skill` 로 다시 패키징해
  **사용자가 Claude 설정에서 재업로드**해야 실행에 반영된다.
- **저장소와 설치본이 다를 수 있다.** 저장소만 고치고 재업로드를 안 했으면
  설치본이 옛것이고, 설치본만 고쳤으면 그 수정은 세션이 끝나며 사라졌다.

**시작하면서 둘을 대조해라.**

```bash
git clone https://github.com/LeeKwanBeom/baemin-review-skill
md5sum baemin-review-skill/SKILL.md "<스킬 호출 헤더의 Base directory>/SKILL.md"
```

- **md5 동일** → 정상. 그대로 진행한다.
- 사용자 폴더(`$HOME/mnt/claude`)의 `baemin-review.skill` 패키지 파일도 최신인지 본다 — 2026-09-09에는 7/26자 패키지가 남아 있어 9/6 개정 이전 것으로 보였다. 오래됐으면 "재패키징 시 이 파일을 갱신할 것"으로 보고에 적는다(실행에는 영향 없음).
- **다름** → 어느 쪽이 최신인지 판정하고 **그 사실부터 보고해라.**
  저장소가 최신이면 "재업로드가 안 된 것"이고, 설치본이 최신이면
  "저장소에 push 가 안 된 것"이다. 둘은 대응이 다르다.
  진단은 **저장소 사본을 기준으로** 하되, 설치본과 다른 부분은 따로 적어라.
- `NO_BASELINE` → "기준선 파일 없음"이라고 명시하고 신규 진단으로 진행한다.

[시작 전 확인 ③ — 실제 실행 없이는 진단이 절반이다]

이 스킬은 브라우저 자동화다. 문서를 읽는 것만으로는 셀렉터가 아직 맞는지,
스크롤이 정체되는지, 파싱이 되는지 판정할 수 없다.
**사용자가 정한 방침이기도 하다: "개선 후 실제 사이트에서 실행 테스트".**

그러므로 이 점검은 **실제 1회 실행을 포함한다.** 다만 조건이 있다.

- **엑셀을 먼저 백업해라.** 이 스킬은 스냅샷 동기화라 실행이 기존 행을 지운다.
  `$HOME/skillwork`는 없을 수 있으니 먼저 만든다(2026-09-09에 없었음).
  ```bash
  mkdir -p "$HOME/skillwork" && cp "$HOME/mnt/claude/배민_저점수리뷰.xlsx" "$HOME/skillwork/배민_백업_$(date +%Y%m%d_%H%M).xlsx"
  ```
- **Step 5(엑셀 저장)는 실행하지 마라.** Step 0~4 까지만 돌리고, 저장 직전에서
  멈춘다. 점검은 진단이지 갱신이 아니다.
- 브라우저·로그인이 준비돼 있지 않으면 사용자에게 요청하고 기다려라.
  계정A(김치찜·곱도리) / 계정B(참 제육) 두 번의 로그인이 필요하다.
- **크롬 창이 다른 창에 가려지지 않게 화면 앞에 두어야 한다.** 새 탭은
  `document.hidden === true`로 시작하는 것이 기본값에 가깝고(2026-09-09 실측 2/2),
  그 상태에서는 타이머가 1초로 늘고 리스트가 로드되지 않는다. SKILL.md Step 2가
  이를 게이트로 잡지만, 점검에서는 **가려진 상태와 꺼낸 상태 둘 다 한 번씩 계측**해
  `throttled` 신호가 뜨고 복구되는지 확인한다(사용자에게 가려달라/꺼내달라 요청).
- **표준 계측(매 회차 고정):** 탭 생성 직후 `document.hidden`, `setTimeout(250)` 실측
  5회, 매장별 `expectedTotal`·`collected`·`blocked`·라운드 수·`avgRoundMs`.
  이 숫자들이 기준선의 "실행 실측 기록"과 대조된다.
- 매장 정보 표(shopId 3개·계정 A/B)는 실행이 통과하면 자동으로 확인된 것이다.
  따로 항목으로 판정하지 않는다(1~3회차 연속 통과).

실행이 불가능하면(브라우저 미연결, 로그인 불가) 그 사실을 명시하고
**실행으로만 확인되는 항목을 전부 [추론]으로 표시해라.** 문서만 읽고
"셀렉터가 맞다 / 스크롤이 정상이다" 라고 쓰지 마라.

[0단계 — 기준선 대조. 신규 진단보다 이걸 먼저]

저장소의 `audit/last-audit.md` 를 먼저 읽어라. 이게 정본이다.
없으면 "기준선 파일 없음"이라고 명시하고 (2)로 넘어가라.

(1) 거기 적힌 항목을 지금 실물에서 하나씩 다시 확인해라.
    해결됨 — 수정 내용이 실물에 있다 (수정된 원문 인용)
    미해결 — 예전 상태 그대로다 (지금 원문 인용)
    근거없음 — 그때 지적 자체가 실물 근거가 없었다 (한 줄 사유)
    요약하지 말고 원문을 붙일 것.

(2) **설치본과 사용자 사본이 어긋났는지 양방향으로 확인해라.**
    - 사용자가 재업로드를 안 했으면 → 지난 회차 수정이 설치본에 없다
    - 설치본에는 있는데 기준선에 기록이 없으면 → 누군가 기록 없이 고친 것
    지난 회차 기준선에 "수정함"으로 적힌 항목이 설치본에 없으면,
    **재업로드가 안 된 것이지 수정이 실패한 게 아니다.** 그 구분을 명확히 적어라.

(3) 그다음에 기준선에 없던 신규 항목만 찾아라.

[직전 회차가 남긴 것 — 기준선의 "다음 점검에서 대조할 것"을 읽어라]

회차마다 이 절에 새 항목을 쓰지 않는다. 직전 회차가 남긴 미확정·미실측 항목은
`audit/last-audit.md`의 "미확정으로 남긴 것"과 "다음 점검에서 대조할 것"에 있다.
그 항목을 0단계 (1)과 같은 방식으로 해결됨/미해결/근거없음 또는 판정완료/미확정으로
다시 판정한다. 저장소 밖 인계 문서(사용자 폴더의 md 등)는 입력물로 쓰되,
다음 회차를 위해 그 내용을 기준선에 흡수하고 나서 끝내라.

(1회차의 인계 A~D·미확정 1~2는 2026-09-09 기준선에 판정·흡수했다. 여기서 다시 다루지 않는다.)

[의도된 동작 — 결함으로 올리지 마라]

아래는 사용자가 알고 선택한 것이거나 SKILL.md "설계 근거"에 이유가 적힌 것이다.
"고치면 좋겠다"는 생각이 들어도 결함이 아니다. 바꾸려면 사용자 승인이 필요하다.

- **엑셀이 스냅샷 방식이라 조회 기간 밖 과거 리뷰가 지워진다.**
  사용자가 알고 선택했다. 이 엑셀은 누적 아카이브가 아니라 최근 현황판이다.
- **API를 쓰지 않고 DOM 을 긁는다.** `self-api.baemin.com` 은 크로스 오리진
  차단이라 헤더를 맞춰도 안 된다(2026-09-05 실측). 쿠팡 방식을 이식하려 하지 마라.
- **조회 기간은 최근 30일 고정.** 7일·14일 대신 사용자가 고른 값이다.
- **게시중단 리뷰는 수집에서 제외한다.** 우리가 신고해 내린 리뷰다.
- **좌표 확인용 스크린샷을 쓰지 않는다.** 뷰포트가 미세하게 바뀌어 좌표가 어긋나고
  타임아웃이 누적된다.
- **엑셀은 플랫폼별로 분리한다.** 쿠팡과 합치지 않는다.
- **날짜는 `YYYY-MM-DD`.** 쿠팡 스킬과 통일한 형식이다.

[되돌리면 안 되는 것 — 이게 그대로 있는지 확인해라]

과거에 사고를 냈던 것들이다. 되돌아가 있으면 그 자체가 결함이다.

| 확인할 것 | 되돌아가면 생기는 일 | 위치(대략) |
|---|---|---|
| `전체\s*\(([\d,]+)\)` — 쉼표 포함 | `\d+` 로 되돌리면 `전체(1,460)` 이 1로 읽혀 1건에서 끝남 | Step 3 |
| `expectedTotal` 의 `0` 과 `null` 구분 | `\|\| 0` 을 붙이면 총건수 실패가 "리뷰 없음"이 되어 기존 엑셀 행이 지워짐 | Step 3·4-3 |
| `ok` 플래그 기본값이 실패 | 저장 스크립트의 `ok_stores` 필터를 빼면 실패 매장이 빈 배열로 동기화돼 저점수가 통째로 사라짐 | Step 4-3·5-2 |
| 카드 경계 `[class*="ReviewContent-module"]` | 부모 walk-up 방식은 이웃 리뷰를 병합해 데이터를 섞음 | Step 4-1 |
| 별점 읽기 순서 `aria-label → data-* → SVG 색상 → img alt` 와 색상 경로의 `c <= 5` 가드 | 2026-09-09 실측: 현재 사이트에는 aria-label 이 없어 **SVG 색상이 실제 주 경로**다(381/381, 이상값 0). aria-label 경로를 지우면 사이트가 되돌아올 때 대비가 없어지고, `c <= 5` 가드를 빼면 병합 카드에서 44 같은 이상값이 다시 나온다 | Step 4-1 |
| Step 2 의 `hidden === true` 게이트 + `_scroll` 의 `throttled` 조기 반환(3라운드 연속 600ms 초과) | 되돌리면 가려진 창에서 190건 중 6건에서 멈추고 예산을 gained 0 으로 소진한다(2026-09-09 실측). "스크린샷으로 깨우기"를 되살리지 말 것 — hidden 을 풀지 못한다 | Step 2·4-1·4-2 |
| Step 0 의 세 검사 분리 출력(`FOLDER_OK`/`OPENPYXL_OK`/`UNLOCKED`) | `A && B && C && echo LOCKED \|\| echo UNLOCKED` 한 줄로 되돌리면 폴더·openpyxl 부재가 `UNLOCKED` 로 찍혀 통과한다 | Step 0 |
| `_parse` 의 `window._blocked` 집계와 4-3 의 `countMatch` | 빼면 `collected + blocked === expectedTotal` 검증을 다시 사람이 하게 된다(2026-09-09: 189+1=190) | Step 4-1·4-3 |
| `ws.delete_rows` | 셀을 None 으로 비우면 빈 행이 누적돼 max_row 가 부풀음(실측 575행 중 실데이터 1행) | Step 5-2 |
| 실패 매장도 배열에 남김 | 사람이 골라내면 저장 스크립트가 판단할 근거가 사라짐 | Step 5-1 |
| `_scroll` 예산 25초 이하 | 45초 CDP 타임아웃에 걸림 | Step 4-1 |
| 챗봇 위젯 `isChatbot` 제외 | 도킹된 챗봇을 팝업으로 오탐해 계속 닫으려 함 | Step 2 |
| 기간 다이얼로그 `isFilterDialog` 스킵 | 우리가 연 필터를 스스로 닫아버림 | Step 2 |

[특히 이런 걸 찾아줘]

■ A. 문서와 코드가 어긋나는 곳
   - 매장 정보 표(shopId 3개·계정 A/B)가 실제 URL·로그인과 맞는지
   - 트러블슈팅 표의 증상·원인·대응이 실제 코드 동작과 맞는지
     (1회차의 "hidden 전제" 오류가 이 유형이었다 — 기준선 결함 1)
   - 실측 수치(2026-09-09 기준: 190건 약 50초·257ms/라운드, 381/381,
     DOM 카드 6~15개, 김치찜 6개월 1점 1건·2점 1건·3점 4건 등)가
     지금도 유효한지. 낡았으면 **측정 일자와 함께** 갱신 대상이다
   - Step 간 값 인계(`expectedTotal`·`filterOk`·`authExpired`)가 끊기는 지점

■ B. 셀렉터·정규식이 현재 사이트와 맞는지  ※ 실행으로만 판정 가능

[결과 정리 방식]

결함을 심각도 순으로, 항목마다:

[수정 회차에 적용할 것 — 이 절은 진단이 아니라 다음 단계용이다]

이번 회차는 진단만 한다. 다만 여기서 나온 결함을 **고칠 때** 아래를 지켜야
같은 회차 안에서 새 결함이 생기지 않는다. 진단 보고서 끝에 이 절을 그대로
옮겨 적어 다음 단계가 읽게 해라.

- **수정은 저장소 `SKILL.md` 에서 한다.** 설치본을 직접 고치면 세션이 끝나며
  사라진다. 저장소에 push 한 뒤 그것으로 패키징해라.
- **한 번의 수정 → 한 번의 패키징 → 한 번의 재설치.**
  중간에 다른 세션을 열면 그 세션은 옛 캐시를 읽고 그 위에 수정한다.
  먼저 한 수정이 조용히 사라진다. 실제로 겪은 사고다.
- **수정 후 반드시 파일을 다시 열어 눈으로 확인하고 나서 "완료"라고 말해라.**
  사용자가 정한 상시 방침이다. 확인 없이 완료를 선언하지 마라.
- **고친 뒤 실제 사이트에서 1회 실행해라.** 사용자가 정한 방침이다.
  문서만 고치고 끝내지 마라.
- **같은 개념을 두 곳에서 고칠 때는 기준을 대조해라.** 이 문서는 절차·코드·
  트러블슈팅 표에 같은 규칙이 세 번 나오는 곳이 있다. 한 곳만 고치면 어긋난다.
- **판정 조건을 완화하는 수정을 했으면 원래 잡히던 실패가 여전히 잡히는지
  다시 확인해라.** `ok` 판정과 `expectedTotal` 관련이 특히 그렇다.
- **"되돌리면 안 되는 것" 표에 있는 것을 건드렸으면 그 표도 같이 갱신해라.**
- **수정과 검증은 다른 세션에서 한다.** 진단한 쪽이 수정하지 않고, 수정한 쪽이
  검증하지 않는다. 다른 스킬 점검에서 검증이 잡아낸 것의 다수가 수정 과정에서
  새로 생긴 것이었다.

[마무리 — 기준선 갱신]

진단이 끝나면 저장소의 아래 두 파일을 갱신하고 push 한다. **커밋은 두 번이다** —
예전 문구("같은 커밋으로")는 "채택 여부를 묻기 전에 checklist.md 를 고치지 마라"와
동시에 성립할 수 없었다(1회차에서 확인). 순서:

1. **1차 커밋(진단 직후, 보고 전):** `audit/last-audit.md` 만. 아래 형식. 직전 회차
   기록은 파일 아래쪽에 "이전 기록" 으로 원문 보존해라. "점검표 개정안"은 이 파일
   안에 제안으로만 적는다. checklist.md 는 이 커밋에서 손대지 않는다.
2. **2차 커밋(사용자가 개정안을 채택한 뒤):** `audit/checklist.md` — 채택된 것만
   반영하고 머리말의 버전 줄을 갱신한다. 수정 회차라면 `SKILL.md` 와
   `last-audit.md` 의 "수정 기록" 절도 이 커밋에 함께 넣는다.

1차만 하고 세션이 끝나면 기준선은 남되 점검표는 옛것이다 — 다음 회차가 last-audit.md
의 개정안 절을 읽으면 복구된다. 2차 없이 끝냈으면 그 사실을 보고에 적어라.

**저장소의 `SKILL.md` 는 진단 회차에 고치지 마라.** 설치본과 md5 가 달랐다면
그 사실만 기준선에 적고, 어느 쪽으로 맞출지는 사용자가 정한다.

**순서를 지켜라: ① push → ② 재clone 확인(md5 대조) → ③ 그다음에 채팅 보고.**
채팅 보고를 먼저 길게 쓰면 세션이 끊길 때 저장소에 아무것도 남지 않는다.

**클라우드에서 push 가 막히면 PC 에서 push 해라.** 2026-09-09 실측: 클라우드
컨테이너의 git 프록시가 이 저장소를 "세션의 인가 저장소 목록에 없음"으로 403 을
냈다(`access denied by the git proxy`). 조직 정책 거부라 재시도해도 안 된다. 절차:
  1. 갱신할 파일을 `SendUserFile` → `device_commit_files` 로 사용자 폴더
     (`$HOME/mnt/claude/`)에 내려놓는다(어차피 "파일로도 내려줘" 요건이다).
  2. `device_bash` 로 PC 에서 clone → 파일 복사 → commit → push:
     ```bash
     mkdir -p $HOME/skillwork && cd $HOME/skillwork && rm -rf repo && git clone -q https://github.com/LeeKwanBeom/baemin-review-skill repo && cd repo
     cp "$HOME/mnt/claude/<내려놓은 파일>" audit/last-audit.md   # 필요한 파일마다
     git config user.email "<이메일>" && git config user.name "LeeKwanBeom"
     git add -A && git commit -q -m "<메시지>" && git push -q https://x-access-token:<토큰>@github.com/LeeKwanBeom/baemin-review-skill.git HEAD:main
     ```
     PC 의 git 은 네트워크가 열려 있었다(git 2.34.1, `git ls-remote` 성공).
  3. 재clone 으로 md5 를 대조하고, "PC 에서 push 했다"는 사실을 보고에 적는다.
  토큰은 명령줄에만 쓰고 remote 설정이나 파일에 남기지 않는다.

**진단 전문을 파일로도 내려줘. 채팅 요약본 말고 파일 자체가 필요하다.**
요약만 받으면 다음 세션으로 옮길 때 절반이 유실된다.

토큰을 못 받았으면 push를 건너뛰되 **두 파일을 반드시 파일로 내려주고**
"저장소에 반영되지 않았다"고 명시해라. 완료라고 말하지 마라.
